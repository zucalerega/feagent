# FEAgent GPU / whole-airplane audit (read-only; paths relative to the repo root)

## 1. What uses a GPU today
- ONLY the linear solve (cuDSS) and the optional NN surrogate. Assembly, BC elimination, stress recovery (assembly of mass matrix, RHS), meshing, geometry analysis, rendering are all CPU/NumPy/SciPy.
- cuDSS: feacore/solver/linsolve.py:15-17 (nvmath.sparse.advanced.direct_solver, SPD), `_solve_cudss` :244-261: host SciPy CSR + NumPy RHS, nvmath copies to device 0 ("execution='cuda'", :258). Single GPU only, device 0 hardwired; no device selection, no multi-GPU, no hybrid-memory/out-of-core options set.
- Selection: explicit method > env FEACORE_LINEAR_SOLVER (linsolve.py:30-31,189-191) > auto. auto picks cudss iff CUDA device visible (cupy/cuda-python probe :107-127) + nvmath importable AND n >= FEACORE_CUDSS_MIN_N (default 20000, :147-155,177-182), else pypardiso, else scipy. CLI: feacore/cli.py:4,41 `--linear-solver`; case: analysis.options['linear_solver']. Failure falls back silently-ish to scipy (notes in LinearSolveReport) unless strict (:343-352).
- Stress recovery's global L2 projection (mass matrix, many RHS) also goes through solve_linear (skfem_backend.py:529) so it can hit cuDSS too; main solve :664. Reaction/QoI/Locator are CPU.
- Direct-only by design (determinism for GCI studies, linsolve.py:5-7). CG/pyamg is CPU opt-in; no GPU iterative (no AMGX/cupy-cg) -> no path past direct-solve memory.
- Install: scripts/setup_gpu_box.sh:55-64 (nvidia-smi present -> `nvmath-python[cu12|cu13]` + cupy-cuda12x/13x, chosen by driver CUDA major). Brev: docs/brev.md (bootstrap.sh -> UI service on :8000; sizing L40S/A100/H100 line 33-38). DGX Spark aarch64: setup_gpu_box.sh:36-47 (conda-forge gmsh, no MKL; cuDSS + scipy only; docs/brev.md:78-80).
- Validation: scripts/gpu_check.py (all methods vs SciPy to 1e-8, gpu_check.py:1-10,TOL). docs/solver_skfem.md:220-221: "cuDSS ... has not been run here (no GPU)"; the test auto-runs on CUDA box. I did not find a recorded GPU timing table anywhere. Note: this laptop (where audit ran) has an RTX 4060 Laptop GPU (nvidia-smi -L), 30 GB RAM; no evidence cudss was ever exercised on it.
- Claimed sizes/timings:
  * benchmarks/gold/README.md:84-86: laptop SciPy L0 ~1 s, L1 (113-146k DOF) ~20 s at 3 GB; "L2 (1.0M DOFs) needs a GPU (cuDSS) or tens of GB". README:6-7: gold generator ran on an H100 (goldgen), L2 = 0.8-1.0M DOFs.
  * docs/solver_skfem.md:184-198 (CPU, 4 shared cores, PARDISO 1 thread): 3D P2 141k DOF wall 21-25 s (solve 13-14 s); 72k scipy 100 s; assembly ~200 us/P2 tet (:203-206). Says cuDSS/multithreaded PARDISO "should cut solve several-fold" (:201-203) - unmeasured.
  * docs/brev.md:33-37: "FEA is mostly CPU-bound: GPU only speeds up large 3D solves (cuDSS) and surrogate training"; recommends 32 vCPU/128 GB/1 GPU for 4 agents.
- Surrogate/NN (GPU, torch): feacore/solver/nn_backend.py:13-14,62-68 (device: option > case option > FEACORE_NN_DEVICE > cuda if available); models cached per (path,mtime,device) :76-78. Training: scripts/train_surrogate.py --device cuda --amp; docs/surrogate.md:104-127 (graph held in RAM ~0.25 MB/1000 nodes), docs/surrogate.md:62-65 PhysicsNeMo path "untested"; :139-140 "no GPU numbers are claimed". Surrogate is 2D/plate-family, "fast but unverified, never the reference" (solver/__init__.py:6); raises UnsupportedCase outside its family (surrogate.md:150). Not applicable to airplane assemblies.
- ace/ on origin/ace-loop: no GPU code. Only reference: ace/field_error.py:36 comment "ACE_FIELD_REFS points it elsewhere (e.g. files built on a GPU box)" - i.e. fine-reference solves are precomputed on a GPU box and cached. Node caps 20-30k (ace/config.py:34-40) - everything the agents do is tiny.
- Thread pinning: OMP_NUM_THREADS=1 set in dataset/validate scripts (e.g. scripts/make_surrogate_dataset.py:29, validate.py:27); UI server records it (server.py:198). No CUDA_VISIBLE_DEVICES handling anywhere in repo (grep: none).

## 3. Concurrency model
- UI server (feacore/ui/jobs.py:54-120): JobRunner with two lanes of Python threads each spawning ONE fresh subprocess per job (jobs.py:183-188, `subprocess.Popen(python -m feacore.ui.worker ...)`, env copied). quick lane default 1 worker (FEACORE_UI_QUICK_WORKERS=1), study lane min(4, cpu//4) (jobs.py:58-62). Timeouts: solve 1800 s, study 4 h (:64-68). So at most ~1 + 1..4 solves at a time per server; additional requests queue in an in-memory queue.Queue (lost on restart; mark_interrupted runstore.py:547). Process isolation: good (gmsh/OCC global state safe), ~1 s startup overhead (ui.md:362).
- GPU sharing: nothing. Every worker process that picks cudss will init its own CUDA context on device 0 and allocate its own factor; no GPU memory accounting, scheduler, or CUDA_VISIBLE_DEVICES pinning. N concurrent big solves on one GPU -> OOM -> fallback to scipy CPU (slow, RAM blowup) per linsolve.py:343-352. NN backend caches models per process only (nn_backend.py:76-78).
- CPU threading: PARDISO/MKL threads default to all cores per process unless OMP/MKL_NUM_THREADS set; UI main only sets/records them (feacore/ui/__main__.py:34, server.py:198). N parallel workers x all-core PARDISO oversubscribes. docs/brev.md:35-38 recommends 32 vCPU for 4 agents.
- Run store (feacore/runstore.py): per-record JSON in directories, atomic write via tmp + os.replace (:105-111), unique ids; no locks, no DB; listing scans directory (ui.md:363). OK for hundreds-thousands of records, not 1e5.
- ACE loop (origin/ace-loop ace/run_loop.py:66-91): ProcessPoolExecutor(concurrency, spawn), one agent run per process, BrokenProcessPool recovery, cost budget stop. LLM-bound; no GPU use. Scoring subprocesses 10-30 s per 3D run (:108). So "many agents in parallel" works on one box (CPU) up to cores/RAM; across boxes there is no remote-worker/queue abstraction (Brev docs: agents on the same box hit localhost:8000; teammates share one box via port forward).
- Auth: single shared token, no rate limits/quotas per agent (ui.md:361).

## 4. Gaps ranked for "whole airplane + parallel agents"
1. No scalable solver path: monolithic single-process direct solve + serial single-thread host assembly/RAM; no domain decomposition/substructuring (Craig-Bampton), no distributed (MPI/PETSc/Trilinos) or GPU iterative (AMGX / cupy-AMG / PCG on GPU) solver. Hard ceiling ~1-8M DOF depending on tier (above). Biggest blocker.
2. Missing physics/element types for airframes: no shells/beams/rigid links/MPC/contact/tied interfaces, only tet4/tet10, linear static; conformal-bonded fragments only. A solid-tet airplane is infeasible in DOFs anyway; need idealisation (shell/beam) + connectors.
3. Assembly-level CAD/mesh pipeline: serial gmsh, global fragment of all solids, single global size field, no per-part/per-volume meshing + conformal-interface stitching or non-conformal ties, no partitioned/parallel gmsh (no NumThreads, no HXT config), ASCII .msh + meshio read of whole file. Geometry analysis/report not designed for 1e3-1e4 volumes (agent context blow-up).
4. GPU path is unproven and fragile: cuDSS never run in repo's recorded docs ("not been run here"), no GPU timing table, device 0 hardwired, no hybrid-memory/multi-GPU (cuDSS supports both), OOM silently falls back to CPU scipy; no memory pre-estimate/guard ("will this fit?") before choosing a solver; assembly stays on CPU so GPU speedup is capped (Amdahl: wall 21 s vs solve 13 s at 141k DOF; assembly+recovery+IO dominate once solve is fast).
5. No GPU/resource scheduling for parallel agents: no per-job GPU/memory reservation, no CUDA_VISIBLE_DEVICES assignment, MKL threads uncontrolled (oversubscription), job queue in-memory single-server, 1 quick-lane worker, no multi-node worker pool; each job is a fresh Python process (~1 s) with cold imports + cuDSS context init each time (no persistent GPU solver service/handle reuse).
6. Mesh/field I/O: ASCII msh, per-run field dumps, JSON run store with directory scans; UI viewer shows surface only, no LOD/per-part selection; fine for current 0.1-1M DOF gold meshes, breaks at 1e7.
7. Evaluation/ACE side: node caps 20-30k, scoring and references designed for small benchmarks; reference fine-solves for an airplane would need a GPU box and cached refs (ACE_FIELD_REFS hook exists but no whole-airframe benchmark; gold set tops out at 1M DOF L2).
8. Surrogate: 2D/plate family only, GPU path untested (surrogate.md:62-65,139-140); no help for assemblies.
Measured-vs-claimed: only CPU timings measured (solver_skfem.md:184-198, gold README); every GPU number is a claim or absent. Memory-per-DOF and DOF-ceilings above are my estimates, not from the repo.
