# Aircraft geometry + meshing at scale (research notes, 2026-10-31)
Legend: [V]=verified from fetched page/search this session; [M]=from memory/unverified, check before relying.

## 1. Downloadable geometry
- **uCRM (undeflected CRM), U-Michigan MDO Lab** — https://data.mendeley.com/datasets/gpk4zn73xn  [V]
  License CC BY 4.0 (cite Brooks, Kenway, Martins, AIAA J. 2018). Contents: wing-body-tail OML in IGES + TIN (uCRM-9 and 13.5 variants);
  CGNS aero meshes; **BDF structural meshes of the aluminium wingbox** (smeared-stiffness blade-stiffened panels, i.e. SHELL elements
  with stiffener effects in the properties, NOT modeled stringers), engine/control-surface masses, cruise aero loads. SI units.
  Mirror: mdolab.engin.umich.edu/content/ucrm. File sizes not visible [unverified; BDFs are MB-scale, [M] coarse ~ tens of k shell elems].
  Internal layout (spars/ribs) exists only as shell panels in the BDF; the IGES is OML only (no internal structure) [M for IGES].
- **NASA CRM** — https://commonresearchmodel.larc.nasa.gov/ (geometry + "FEM file" pages) [V]. Offers wingbox FE models
  (e.g. CRM_V12wingbox_1, V15wingbox_1_noHM), NTF wind-tunnel model FEMs (wing/body, +HT, +nacelle/pylon; 30-mode modal for HT config). Formats not stated
  on page; HyperMesh files removed for V14/V15, request s.m.rivers@nasa.gov. No explicit license/ITAR statement on page (NASA-authored => generally public domain, but confirm per page).
  OML geometry also at nasa.gov/common_research_model/high-speed-crm/geometry/.
- **pCRM9 NASTRAN wing (Zenodo 6390714 / doi 10.5281/zenodo.6384059)** [V existence]: derivative of uCRM, NASTRAN SOL103 deck, separate material/property/rib files; RBE2s removed. Check Zenodo license field.
- **OpenVSP** (software: NASA Open Source Agreement 1.3 [V]; GitHub nasa/openvsp archived, active repo github.com/OpenVSP/OpenVSP [V partially]).
  Hangar closed end-2023; models ported to **VSP Airshow** (launched Aug 2024) [V via secondary sources]. Per-model licenses not confirmed -- check each.
  NASA lists "X-57 Maxwell VSP3 Model" (2025) under X-57 technical docs: https://www.nasa.gov/aeroresearch/X-57/technical/index.html [V listing; link/license unverified]. OpenVSP ships example .vsp3 in its repo/install (examples dir, NOSA) [M].
  .vsp3 = XML, a few hundred KB. OML only; structure is added via FEA Mesh tool (below).
- **ABC / Fusion 360 Gallery / DeepCAD / SimJEB**: component-level parts (brackets), not airframes. SimJEB (GE jet engine brackets, dataverse.harvard.edu; already in repo benchmarks). ABC license is non-commercial research; not useful for whole aircraft [M].
- **GrabCAD / NASA 3D resources / Sketchfab**: lots of airplane STEP; per-upload licenses vary, GrabCAD ToS limits redistribution -> do not commit to repo; use only locally. Mostly OML-only or unwatertight multi-body assemblies [M].
- DLR: DLR-F6/F4/F25 wing-body OML (AIAA DPW/HiLiftPW) public for CFD, OML only [M]. ONERA M6 trivial wing; ONERA OAT15A. DLR D150 (Airbus-like) published with FE (not verified) [M]. Boeing/Airbus: no open internal structure.
- Takeaway: **real internal structure with open license = uCRM BDF shells** or **self-generated via OpenVSP FEA Mesh / parametric script**. No open STEP of a full airframe with ribs/spars/stringers found.

## 2. OML + layout -> FE geometry
- OpenVSP Python API (pip openvsp / vsp python modules ship with release; `import openvsp as vsp`) [V group FEA Mesh API: https://openvsp.org/api_docs/latest/group___f_e_a_mesh.html].
  Flow: vsp.ReadVSPFile -> vsp.AddFeaStruct(geom_id) -> vsp.AddFeaPart(geom_id, struct_idx, vsp.FEA_RIB / FEA_SLICE / FEA_SPAR / FEA_FIX_POINT / FEA_SKIN ...) -> set params via vsp.GetParm/SetParmVal (PerU, Thickness, ...) ->
  vsp.SetFeaMeshStructIndex + vsp.ComputeFeaMesh(geom, struct, vsp.FEA_NASTRAN_FILE_NAME or FEA_CALCULIX_FILE_NAME or FEA_STL/GMSH) [V]. VSP's own mesher is CFD-grade 2D shell (CART3D-ish surface mesher), tri/quad shells, + beam. Also GMSH export type exists [M].
  STEP: maintainer (2025 Google group) lists 4 routes: untrimmed OML STEP; untrimmed FEA-structure STEP; trimmed "Export CAD" from FEA Structure; Nastran/CalculiX mesh. Ribs/spars come out as **thin surfaces**, not solids [V: groups.google.com/g/openvsp/c/Ud1fsCWPQos]. Trimmed spar STEP reportedly flaky in some CAD [V: .../nz7Uyh6o4Uk]; advice: export untrimmed + trim in a CAD kernel. Python call: vsp.ExportFile(path, vsp.SET_ALL, vsp.EXPORT_STEP) with STEP options (split surfaces, merge points, tolerance, "export structure") [M on exact option names; check api docs].
- OpenCASCADE route (what our harness already uses via gmsh/OCC): take OML STEP from VSP, build spar/rib planes as boxes/planes, `BooleanFragments` to cut the wing solid into bays + thicken skins by offsetting inner surface (gmsh `occ.offset`? not robust; better: build skin as OML minus inner-offset solid). Parametric wingbox in cadquery/OCC script is more reliable than VSP STEP for solids [M].
- ESP/EGADS + pyCAPS (NASA/MIT/Syracuse, ESP open source, LGPL-ish) : `pip`-less; build from source. CAPS has `aflr`, `egadsTess`, `masstran/mystran/nastran` AIMs, `awave`, `fun3d`; ESP "wingbox" / OpenCSM examples (`wing` + `.csm` with ribs/spars, Boolean ops) produce *solid* bodies and shell meshes natively. VSP also has an OpenCSM/ESP export [M]. Good if we want solid wingbox with robust Booleans; heavier install.
- NASA tools: OpenMDAO/pyOptSparse/TACS (uCRM is TACS's showcase, shells), pyGeo/pyLayout (MDO Lab, Apache; generates wingbox FE from OML+layout, to BDF) [M].
- **Shell vs solid**: aircraft primary structure is thin-walled (skin 2-6 mm over meters). Proper modeling = shell (2D) + beam stiffeners; that's what uCRM BDF and all industry FEMs do. 3D tets across a 3 mm skin need >=2-3 quadratic tets through thickness => aspect ratio killer; counts explode (see 3). Solid tets are defensible for: fittings, lugs/wing-fuselage attach, brackets, thick wing root, or a *stubby/coarse demo* wingbox with exaggerated thickness (e.g. 20-30 mm skins) as pipeline demonstration. Our harness/solver is solid tet only, so: (a) stage a thick-skin demo, (b) add shell element support (tri/quad S3/MITC or DKT) to solver as a separate feature if "real" aircraft FEA is the goal; flag this as the big gap. Alternative: use uCRM BDF directly as a *reference/benchmark* (compare displacement/frequencies to published) rather than meshing it.

## 3. Meshing at scale (gmsh)
- Threads [V partial: gitlab.onelab.info gmsh issues/2789, fenics discourse 3756, prepomax 2761]: `General.NumThreads`, `Mesh.MaxNumThreads1D/2D/3D`. 1D/2D run coarse-grained across curves/surfaces; **3D parallel only for HXT** (`Mesh.Algorithm3D=10`), fine-grained within a volume, OpenMP. Caveat: HXT results non-repeatable when threads>1 (issue 2789) -> pin thread count, and our harness's determinism gates/hashes need that. HXT needs a valid 2D surface mesh and is fast (~millions tets/min on many cores) but quality is lower than Delaunay (Algo 1) -> optimize with `gmsh.model.mesh.optimize("Netgen")`/ "HighOrder"; Delaunay/Frontal (1,4) are serial. Memory grows with thread count. Python API: `gmsh.option.setNumber("General.NumThreads", n)`; the multi_thread.py API example in gmsh shows threaded user code (not necessary).
- Partitioning: `gmsh.model.mesh.partition(N)` (METIS default, `Mesh.PartitionCreateTopology`, `PartitionCreatePhysicals`, `PartitionSplitMeshFiles`); writes partitioned MSH4 (one file or per-partition with ghost cells). Use for MPI/domain-decomp solve, NOT for meshing parallelism. [M, standard gmsh docs; verify on installed version]. Needs gmsh built with METIS (pip wheel has it [M]).
- Binary I/O: `Mesh.Binary=1`, `Mesh.MshFileVersion=4.1` -> binary MSH4; large speedup/size cut vs ASCII; meshio/gmsh read both. Node/element tags 64-bit supported in 4.x.
- **Parallel strategy**:
  (A) One conformal assembly: OCC `fragment` (BooleanFragments) all parts -> shared faces -> gmsh meshes all volumes conformally in one process; 3D via HXT multi-thread. Pro: no interface treatment, solver is trivially one K matrix. Con: single process, fragmenting hundreds of parts is slow/fragile (tolerance, sliver faces), one agent can't edit one part independently, any part change re-meshes all. Our harness already does this for multi-volume STEP.
  (B) Parts meshed independently in separate processes (multiprocessing / one agent per part, each writing binary MSH4 + report.json), then assembled non-conformally: tied contact / mortar / MPC constraints between interface surfaces (node-to-surface penalty or mortar), or **conformal-by-construction**: mesh interface faces once (shared 2D mesh from a "interface mesh" step) and impose it as transfinite/discrete-surface constraint on both neighbors. Needs solver support for tie constraints (not present today presumably). Pros: embarrassingly parallel, matches per-part agent model, localized re-mesh. Cons: tie accuracy (consistent only with mortar), more solver work, interface gap/overlap tolerances.
  Recommended hybrid for hackathon: keep conformal at sub-assembly level (wing box = skins+spars+ribs fragmented, ~20-100 volumes), parallelize *across* sub-assemblies (wing, fuselage section, tail) via process pool and join through tied interfaces (few, planar bolted/attach planes). Merge by node-coincident interface meshes if the attach faces use identical edge discretization (agent can specify the same `size` + transfinite on both).
- Expected sizes (rough engineering estimates, [M] computed not cited): wingbox half-wing CRM scale (span ~29 m half, root chord ~13 m, box ~ 60 m^3 envelope but skins/spars ~ 0.25-0.5 m^3 material). With solid tets, quadratic tet10 across a 4 mm skin needs h ~ 2-3 mm through thickness => absurd (>1e9). Practical: thick-skin demo (25 mm skin, h ~ 12 mm in-plane h 30-50 mm): ~0.5-3 M tet4 / 0.1-0.5 M tet10 for a half wingbox with ~20 ribs, 2-3 spars. Fuselage barrel section 5 m long, frames + skin solids at similar thickness: ~1-5 M tets. Full aircraft solids: 1e7-1e8 -> GPU solver territory; shell model of full aircraft (uCRM-style) is 1e4-1e6 DOF -- trivial. gmsh 3D HXT on 22 cores ~ 1-5 M tets/min [M]; 2D surface meshing of thin thin-feature solids is the real bottleneck + failures.

## 4. Staged target (hackathon)
- Stage 0 (hours): generate wingbox procedurally (cadquery/OCC or OpenVSP wing + FEA struct export) as N parts: top skin, bottom skin, front spar, rear spar, 8-12 ribs, with exaggerated thickness 15-30 mm. Also validate on uCRM BDF as shell reference (read with pyNastran; compare tip deflection under cruise load in BDF) -- gives an "answer key".
- Stage 1: per-part agents via harness (`feagent automesh` per part, name faces: attach faces by `{"plane": ...}` query, root clamp). Conformal at wingbox level via fragment, parts meshed with HXT 4-8 threads per process x several processes. Assemble -> single MSH4 -> solve (clamp root, tip/pressure load). Gate: mesh gates + displacement vs thin-beam estimate + (optionally) coarse shell reference.
- Stage 2: wing + fuselage section joined at 2-4 attach lugs/ fittings (solid lugs, tied interface); fuselage as thick ring frames + skin (still solid). Introduces non-conformal ties -> implement penalty/MPC tie in solver, or share-node coincident interface meshes.
- Skip: stringers as separate solids (smear/skip), fasteners, composite layups, fairings, control surfaces/hinge kinematics, landing gear, engines (use point masses/ RBE-like lumped mass), aeroelastic loads (use prescribed pressure), contact, fillets at rib-skin joints (defeat meshing), true full-fidelity thin skins in 3D tets. Do not rely on OpenVSP trimmed STEP structure (flaky) -- use untrimmed + own Boolean/fragment in OCC.
- Biggest risks: thin-wall solid meshing blowup (add shell elements or thick demo), STEP boolean robustness on sliver ribs/skin, tet count growth vs solver, HXT nondeterminism, licenses of Hangar/Airshow/GrabCAD models.
